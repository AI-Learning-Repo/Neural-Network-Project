# Sprint 2 Planning

Planning takes place in each original project group's Zoom breakout room. Use the Sprint 1 results, feedback, and shared Jigsaw findings to review the Product Backlog and agree on a realistic Sprint 2 plan.

Record the following six planning requirements in the group's shared project documentation.

## Minimum planning requirements

1. **Sprint Goal**

   - Define what the group intends to achieve by the Sprint 2 Review in Week 5.
   - Explain how Sprint 2 will improve the existing product and provide additional value to its users.

2. **Sprint 2 Backlog**

   - Select and prioritize items from the Product Backlog.
   - Include the required Sprint 2 improvements:
     - Preserve and improve the Sprint 1 functionality: LLM, tools, API integration, and database.
     - Integrate an MCP server and MCP client into the existing assistant.
     - Develop a Streamlit GUI for interacting with the assistant.
     - Implement unit tests for the functions.
     - Continue evaluating the assistant, including its new MCP functionality.

3. **Tasks and Responsibilities**

   - Break selected backlog items into manageable implementation tasks.
   - Identify the team members responsible for each task.
   - Provide rough estimates and identify dependencies.
   - Ensure that all team members contribute to technical development.

4. **Timeline and Milestones**

   - **Week 3:** Begin MCP client/server development and investigate integration into the existing assistant.
   - **Week 4:** Complete MCP integration, Streamlit functionality, and testing.
   - **Week 5:** Finalize integration, conduct evaluation, fix important issues, and prepare the Sprint 2 demonstration and presentation.

   Teams may organize the work differently, provided the planned scope is realistic.

5. **Acceptance Criteria and Evaluation**

   - Define how the group will determine whether each selected backlog item is complete.
   - Identify representative test cases for the assistant, including the MCP workflow.
   - Plan how to verify that existing Sprint 1 functionality still works.
   - Include evidence of function unit testing and assistant-level evaluation.

6. **Risks and Definition of Done**

   - Identify important technical risks, dependencies, and possible blockers.
   - Agree on a Definition of Done: functionality is integrated, runnable, tested, committed to GitHub, documented, and ready to demonstrate.
